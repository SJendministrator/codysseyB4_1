## 2. 수행 내역 (설정 · 명령어 기록)

### 2-1. SSH 설정 — `setup/01_ssh.sh`

| 설정 | 값 | 파일 |
|---|---|---|
| `Port` | 22 → **20022** | `/etc/ssh/sshd_config` (원본 `sshd_config.orig` 보관) |
| `PermitRootLogin` | **no** | 〃 |

```bash
sed -i -E 's|^[#[:space:]]*Port[[:space:]].*|Port 20022|' /etc/ssh/sshd_config
sed -i -E 's|^[#[:space:]]*PermitRootLogin[[:space:]].*|PermitRootLogin no|' /etc/ssh/sshd_config
sshd -t                       # 문법 검사 — 틀린 설정으로 재시작하면 SSH 가 아예 안 뜬다
systemctl restart ssh
sshd -T | grep -E '^(port|permitrootlogin) '   # 파일이 아니라 "실제 적용값" 확인
ss -tulnp | grep sshd
```

- `sshd_config.d/*.conf` 드롭인 파일이 먼저 읽히고 **먼저 나온 값이 이긴다**. 드롭인에 같은 키가 있으면 메인 파일 수정이 무시되므로 스크립트가 충돌 여부를 검사한다.

```
$ grep -nE '^(Port|PermitRootLogin)[[:space:]]' /etc/ssh/sshd_config

$ sshd -T | grep -E '^(port|permitrootlogin) '

permitrootlogin no

$ ss -tulnp | grep -E 'sshd|:20022'
```

### 2-2. 방화벽 (UFW) — `setup/02_firewall.sh`

```bash
ufw --force reset
ufw default deny incoming
ufw default allow outgoing
ufw allow 20022/tcp           # enable 전에 먼저 허용 (원격 접속 중이면 끊기지 않게)
ufw allow 15034/tcp
ufw --force enable
ufw status verbose
```

```

Default: deny (incoming), allow (outgoing), deny (routed)
New profiles: skip
```

### 2-4. 디렉터리 · 권한 · ACL — `setup/03_accounts.sh`

| 경로 | 소유자:그룹 | 모드 | ACL | 의미 |
|---|---|---|---|---|
| `/home/agent-admin` | agent-admin:agent-admin | 750 | `g:agent-common:--x` | 목록은 못 보고 **통과만** 허용 |
| `$AGENT_HOME` | agent-admin:agent-common | 2750 | | |
| `$AGENT_HOME/upload_files` | agent-admin:agent-common | 2770 | `g:agent-common:rwx` + default | **공유**: admin·dev·test 읽기·쓰기 |
| `$AGENT_HOME/api_keys` | agent-admin:agent-core | 2770 | `g:agent-core:rwx` + default | **보안**: admin·dev 만 |
| `$AGENT_HOME/bin` | agent-dev:agent-core | 2750 | | dev 작성, core 실행 |
| `/var/log/agent-app` | agent-admin:agent-core | 2770 | `g:agent-core:rwx` + default | **보안**: admin·dev 만 |

```bash
install -d -o agent-admin -g agent-common -m 2770 $AGENT_HOME/upload_files
setfacl -m g:agent-common:rwx $AGENT_HOME/upload_files
setfacl -d -m u::rwx,g::rwx,g:agent-common:rwx,o::--- $AGENT_HOME/upload_files   # 앞으로 생길 파일
setfacl -m g:agent-common:--x /home/agent-admin
getfacl -p $AGENT_HOME/upload_files
```

- **2xxx (setgid)**: 디렉터리 안에서 만든 파일이 만든 사람의 기본 그룹이 아니라 **디렉터리 그룹**을 물려받는다. 없으면 agent-test 가 만든 파일의 그룹이 `agent-test` 가 되어 다른 사람이 못 고친다.
- **default ACL**: 만드는 사람의 umask(보통 022, 그룹 쓰기 없음)와 관계없이 새 파일에 그룹 쓰기 권한이 붙는다.
- **홈 디렉터리 통과 권한**: Ubuntu 22.04 홈은 750 이라 dev·test 는 `/home/agent-admin` 을 지나갈 수 없어 `upload_files` 에 도달하지 못한다. `r`(목록) 없이 `x`(통과)만 준다.

| 변수 | 값 |
|---|---|
| `AGENT_HOME` | `/home/agent-admin/agent-app` |
| `AGENT_PORT` | `15034` |
| `AGENT_UPLOAD_DIR` | `$AGENT_HOME/upload_files` |

| `AGENT_LOG_DIR` | `/var/log/agent-app` |

- 등록 위치: `/etc/profile.d/agent-app.sh` (원본: `config/agent-app.env`)
- 키 파일: `$AGENT_HOME/api_keys/secret.key`, `agent_api_key_test` 1줄, agent-admin:agent-core 640 (문서상 이름 `t_secret.key` 는 같은 파일을 가리키는 심볼릭 링크)
- **문서와 앱의 차이**: 미션 문서는 `AGENT_KEY_PATH` 를 키 **파일** 경로로 안내하지만, 처음 그대로 설정하자 앱이 `[2/5] Verifying Environment Variables [FAIL] — Key Path Mismatch. Expected: /home/agent-admin/agent-app/api_keys` 로 부팅을 거부했다. 앱이 요구하는 대로 **디렉터리** 경로로 바꾸자 이번엔 `[3/5] Checking Required Files [FAIL] — Missing File: secret.key` 가 나왔다. 앱은 파일 이름도 `t_secret.key` 가 아니라 `secret.key` 를 찾는다. 실제 파일을 `secret.key` 로 만들고, 문서 기준 이름 `t_secret.key` 는 링크로 남겨 두 기준을 모두 만족시켰다. **문서보다 실제 프로그램의 오류 메시지가 정답**이라는 점을 보여주는 사례.

### 2-6. monitor.sh — `bin/monitor.sh` → `$AGENT_HOME/bin/monitor.sh`

| 요구사항 | 구현 |
|---|---|
| 위치·권한 | `$AGENT_HOME/bin/monitor.sh`, agent-dev:agent-core, **750** |
| 프로세스 확인 (실패 시 exit 1) | `pgrep -f` 로 명령줄 맨 앞이 앱 실행 파일인 프로세스 |
| 포트 확인 (실패 시 exit 1) | `ss -Hltn "sport = :15034"` |
| 방화벽 (경고만) | root: `ufw status` / 일반 계정: `/etc/ufw/ufw.conf` 의 `ENABLED=yes` + `ufw.service` 활성 또는 부팅 시 자동 시작 |
| CPU | `/proc/stat` 1초 간격 2회 → `1 − idle 증가량 / 전체 증가량` |
| MEM | `/proc/meminfo` → `(MemTotal − MemAvailable) / MemTotal` |
| DISK | `df -P /` 의 Use% |
| 임계 경고 | CPU > 20%, MEM > 10%, DISK > 80% → `[WARNING]` |
| 로그 | `[YYYY-MM-DD HH:MM:SS] PID:… CPU:…% MEM:…% DISK_USED:…%` |
| 용량 관리 | 10MB 이상이면 `monitor.<시각>.log` 로 회전, 총 10개 초과분 삭제 (스크립트 로직) |

- `monitor.log` 와 같은 폴더에 생긴 파일도 디렉터리의 default ACL 덕분에 `agent-core` 그룹 rw 로 만들어졌다.

## 3. 과제 목표 — 설명

### SSH 포트 변경과 Root 원격 접속 차단이 왜 기본 보안인가

인터넷에 열린 서버는 22번 포트로 **자동화된 무작위 로그인 시도**를 쉴 새 없이 받는다. 포트를 바꾸면 이런 대량 스캔의 대부분을 피해 로그와 부하가 줄어든다(완벽한 방어는 아니고 노출을 줄이는 것). root 는 **모든 서버에 반드시 있는 이름**이라 공격자가 계정명을 추측할 필요가 없고, 뚫리면 곧바로 시스템 전체 권한이다. root 원격 로그인을 막으면 공격자는 계정명과 비밀번호를 모두 맞혀야 하고, 관리자는 일반 계정으로 들어와 필요할 때만 `sudo` 를 쓰게 되어 **누가 무엇을 했는지 기록**도 남는다.

### "필요 포트만 허용" 방화벽을 어떻게 구성·검증했나

기본 정책을 **들어오는 연결 전부 차단**으로 두고 SSH(20022)와 앱(15034)만 예외로 연다. 이렇게 하면 나중에 실수로 다른 서비스(DB 등)를 띄워도 외부에 노출되지 않는다. 원격 접속 중이라면 20022 를 먼저 허용한 **뒤에** 활성화해야 자기 접속이 끊기지 않는다. 검증은 `ufw status verbose` 로 정책과 규칙을 확인하고, 스크립트가 허용 목록이 정확히 두 개인지 비교한다.

### 역할 기반 계정·그룹과 ACL 로 공유/보안 디렉터리를 나누는 이유

**최소 권한 원칙**: 각자 일에 필요한 만큼만 접근한다. 업로드 파일은 QA 를 포함한 모두가 다뤄야 하지만, API 키와 운영 로그는 유출·변조되면 서비스 전체가 위험하므로 운영·개발(agent-core)만 접근한다. 권한을 사람마다 주지 않고 **그룹에** 주면, 사람이 들어오고 나갈 때 그룹 소속만 바꾸면 된다. ACL 을 쓴 이유는 기본 권한(소유자/그룹/기타 3칸)으로는 "그룹 하나 + 앞으로 생길 파일까지"를 표현하기 어렵기 때문이다(default ACL).

### 환경 변수로 실행 환경을 고정하는 이유와 검증

경로·포트를 코드에 박아두면 서버가 바뀔 때마다 코드를 고쳐야 하고, 사람마다 다른 값으로 실행하는 사고가 난다. 환경 변수로 빼면 **같은 프로그램을 설정만 바꿔** 어디서든 같게 띄울 수 있다. 값은 `config/agent-app.env` 한 곳에서 관리해 로그인 셸(`/etc/profile.d`)과 cron(스크립트가 직접 로드) 모두 같은 값을 쓴다. 검증은 `sudo -iu agent-admin` 으로 **실제 실행 계정의 로그인 셸**에서 `env | grep AGENT_` 를 확인하고, 앱 Boot Sequence 의 `Verifying Environment Variables [OK]` 로 앱 입장에서도 확인한다.

### 쉘 스크립트로 상태를 수집하고 로그로 남겨 문제를 추적하는 흐름

`monitor.sh` 는 ① 앱이 살아 있는지(프로세스·포트) → ② 방어선이 켜져 있는지(방화벽) → ③ 자원이 넉넉한지(CPU·MEM·DISK) 순서로 확인하고, 결과를 **시각이 찍힌 한 줄**로 남긴다. 한 줄 형식이 고정돼 있어 `report.sh` 처럼 나중에 기간별 평균·최대를 뽑을 수 있고, 장애가 나면 "언제부터 이상했는지"를 로그로 거슬러 올라갈 수 있다. 앱이 죽었을 때도 `[ERROR]` 줄을 남기므로 다운 시각이 기록된다. (이전 미션에서 로그 없이는 원인을 추정할 수밖에 없었던 경험과 같은 맥락)

### crontab 주기 실행과 로그 보존 정책이 필요한 이유

사람이 매분 명령을 칠 수는 없다. cron 으로 돌리면 **아무도 보고 있지 않을 때의 상태**도 기록된다. 다만 cron 은 로그인 셸이 아니라서 PATH 와 환경 변수가 거의 비어 있다 — 터미널에서는 되던 스크립트가 cron 에서만 실패하는 흔한 원인이라 crontab 에 PATH 를 쓰고 스크립트가 환경 변수를 직접 읽게 했다. 로그는 계속 쌓이면 **디스크를 가득 채워 오히려 서비스를 멈추게** 하므로, 크기 기준(10MB×10개)으로 상한을 두고, 시간 기준(7일 압축, 30일 삭제)으로 오래된 기록은 작게 보관하다가 정리한다.

## 5. 진행 중 만난 문제와 해결

| 증상 | 원인 | 해결 |
|---|---|---|
| 앱 부팅 `[2/5] Verifying Environment Variables [FAIL] — Key Path Mismatch. Expected: .../api_keys` | 미션 문서는 `AGENT_KEY_PATH` 를 키 **파일** 경로로 안내했지만 앱은 **디렉터리**를 기대 | `AGENT_KEY_PATH=$AGENT_HOME/api_keys` 로 변경 |
| 이어서 `[3/5] Checking Required Files [FAIL] — Missing File: secret.key` | 앱이 찾는 파일 이름은 `t_secret.key` 가 아니라 `secret.key` | 실제 파일은 `secret.key`, 문서 이름 `t_secret.key` 는 심볼릭 링크로 유지 |
| `01_ssh.sh` 가 설정이 맞는데도 `PermitRootLogin 이 no 가 아닙니다` 로 실패 | `set -o pipefail` 아래에서 `sshd -T \| grep -q` — grep 이 찾자마자 끝나면 sshd 가 SIGPIPE 로 끊겨 파이프 전체가 "실패" 판정 | 명령 출력을 변수에 먼저 받은 뒤 검사 |
| cron(agent-admin)에서만 방화벽이 `inactive` 경고 | 일반 계정은 `ufw status` 불가 → `systemctl is-active ufw` 로 판단했는데, `ufw.service` 는 부팅 때 한 번 실행되는 oneshot 이라 `ufw enable` 직후엔 inactive 로 보임 | `ENABLED=yes` + (`is-active` **또는** `is-enabled`) 로 판단 |
| 증거 수집 중 수동 실행이 `이번 회차는 건너뜁니다` 로 끝남 | 마침 같은 초에 cron 회차가 실행 중이라 동시 실행 방지(flock)가 동작 | 바로 포기하지 않고 최대 10초 기다리도록 변경 (`flock -w 10`) |
| 프로세스 검사가 앱이 아닌 셸까지 잡음 (사전 테스트) | `pgrep -f` 가 명령줄 어디든 앱 이름이 있으면 매칭 | 명령줄 **맨 앞**이 앱 실행 파일일 때만 인정 |
| 일반 계정이 `upload_files` 에 접근 못 함 (설계 단계) | Ubuntu 22.04 홈 디렉터리 기본 권한 750 | `/home/agent-admin` 에 agent-common **통과(x)** 권한만 ACL 로 부여 |
